# 抖店多店铺管理后台 · 实施路线图

> **For agentic workers:** 本文件是总路线图，不直接执行。每个里程碑开工前单独写一份任务级计划
> （首个见 [M1 后端](2026-11-25-m1-backend.md) / [M1 前端](2026-11-25-m1-frontend.md)），
> 再用 superpowers:subagent-driven-development 或 superpowers:executing-plans 逐任务实施。

**Goal:** 按里程碑把 [docs/design/](../../design/overview.md) 的设计落成可在出单机双击启动的多店管理后台。

**Architecture:** 单机单进程：FastAPI 后端（`api → service → adapter / store / domain`）代理所有抖店请求，
SQLite 存储，Playwright + 系统 Edge 负责扫码与浏览器通道；React 前端只调本地 API。每个里程碑同时交付后端与对应页面。

**Tech Stack:** Python 3.12、FastAPI、Pydantic v2、curl_cffi、Playwright、SQLAlchemy 2 Core、Alembic、structlog、
pytest；React 19、TypeScript、Vite、Tailwind CSS 4、Arc、TanStack Query、Vitest。

**Spec:** [docs/README.md](../../README.md)（索引）、[docs/design/](../../design/overview.md)、[docs/api/](../../api/README.md)、
[docs/engineering-rules.md](../../engineering-rules.md)、[docs/gaps.md](../../gaps.md)

## 3. 各里程碑范围与完成标准

### M1 基础 + 只读订单

- 范围：[M1 后端计划](2026-11-25-m1-backend.md)、[M1 前端计划](2026-11-25-m1-frontend.md)。
- 完成标准：
  1. 在开发机上添加 2 个店铺、各自扫码登录，`session` 表中 cookie 与 `__token` 为密文。
  2. 两店的发货地址 / 面单账户 / 面单模板 / 快递公司同步入库，界面可见。
  3. 待发货订单每 5 分钟自动同步；两店订单出现在同一列表，可按店筛选。
  4. 人为让一店会话失效，5 分钟内该店标记 `needs_login`，另一店同步不受影响（验收标准第 4 条）。
  5. 所有外部调用写入 `audit_log`，日志中无明文 cookie / 手机号（验收标准第 6 条）。
  6. CI：文件长度、敏感信息、后端分层三项守门脚本在主分支通过。
  7. 首次打开进入「创建管理员」；未登录访问任何后台页面或 `/api/*` 都被拦截；连续 5 次输错密码锁定 5 分钟。

### M2 取号

- 前置：API-04、API-19、API-21 有结论；API-06 补测「取号后不发货」的订单。
- 范围：`backend.md` 5.5 / 5.11 / 5.12，`flows.md` 7.3；表 `waybills`、`tasks`；本地 API `labels/*`；打单台页面。
- 完成标准：验收标准第 2、3 条；作废后能再次取号；取号超时后通过查回恢复且不重复取号；演练模式不发写请求。

### M3 打印

- 前置：出单机可用；API-07（借页面打印可行性）有结论。
- 范围：`flows.md` 7.4 / 第 10 节；表 `print_job`。
- 完成标准：验收标准第 10 条；P3 闭环可用；P1 验证通过则为默认路径。

### M4 发货 + 对账

- 范围：`backend.md` 5.6 / 5.8，`flows.md` 7.5 / 7.6，[api/reconcile.md](../../api/reconcile.md)；表 `order_fact`、`reconcile_findings`。
- 完成标准：验收标准第 1、5 条（2 店各 1 单全流程；对账发现三类异常）。

### M5 只读聚合

- 范围：`backend.md` 5.10，[api/](../../api/README.md) 附录 D / E / F；四类快照表。
- 完成标准：任一店铺上游失败时，其余店铺照常展示，失败店标注 `source: local_db` 与错误。

### M6 经营仪表盘

- 范围：[dashboard.md](../../design/dashboard.md)；表 `shop_daily_stats`、`product_daily_stats`、`shop_status_snapshot`。
- 完成标准：dashboard.md 第 0 节「已验证字段即可」一行全部上线；周 / 月比率按分子和 ÷ 分母和计算。

### M7 打磨与交付

- 范围：B.3 工程能力、ENG-04 / 06 / 07。
- 完成标准：验收标准第 7、11 条（出单机双击启动；演练模式无真实写请求）。

## 4. 并行与分工

| 线 | 内容 | 谁 |
|---|---|---|
| 验证线 | 按里程碑顺序清 gaps.md 的 API 项：先 M2 的 API-04 / 19 / 21 / 06，再 API-07、API-23 | 有真实店铺与测试单的人 |
| 后端线 | M1 后端 → M2 框架 → M2 接口 → M4 | 开发 |
| 前端线 | M1 前端 → 各里程碑页面 | 开发 |
| 工程线 | CI 守门（ENG-05）随 M1；打包（ENG-04）在 M3 后在出单机试一次 | 开发 |

验证线与 M1 同时启动，M1 做完时 M2 的阻塞项应已清掉。

## 5. 风险

| 风险 | 应对 |
|---|---|
| M2 阻塞项迟迟验证不了 | M2 框架（两步提交、幂等、任务表、恢复流程）先用 ReplayTransport 做完，接口层最后接 |
| 借页面打印不可行 | 维持 P3 手动补打，不影响闭环（flows.md 第 10 节） |
| `searchlist` 不能按支付时间筛选 | 仪表盘从上线日起积累历史（dashboard.md 第 0 节） |
| 开发机（macOS）与出单机（Windows）差异 | 凭证加密抽象出开发用实现；浏览器通道与打印在出单机做一次端到端验证（M3） |
| 平台风控 | 每店串行、限速、写接口两步提交、异常即停（flows.md 第 9 节） |
