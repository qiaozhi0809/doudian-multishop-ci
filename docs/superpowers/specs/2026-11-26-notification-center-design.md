# 通知中心（右上角铃铛）设计

## 1. 为什么做

侧栏底部的「任务」面板默认收起：触发了打单 / 发货 / 打印，进度和结果藏在面板里，第一时间看不到；数据只在浏览器内存里，刷新即丢。更重要的是，店铺登录失效、出口异常、新售后 / 退货这类需要马上处理的事，现在只在店铺管理页的状态标签上变化，人不在那一页就不知道。

所有者要的：**存下来的事件记录 + 第一时间看得到的通知，并按轻重分档提醒**。

## 2. 目标 / 非目标 / 反目标

**目标**
- 右上角铃铛：未读数、通知列表（可回看历史、已读 / 未读、点一条跳到对应页面并带筛选）。
- 后端持久化通知；关掉页面期间发生的事，下次打开仍在。
- 新事件：新订单、新售后 / 退货（后端在同步时识别新增）。
- 三档提醒强度（见第 4 节），强提醒「问题不解决不消失」。
- 原「任务」功能全部迁入：批量操作进行中的进度、结束汇总；侧栏「任务」入口删除。

**非目标**
- 不做手机推送、短信、邮件、企业微信等站外通知。
- 不做通知规则自定义编辑器（档位固定，见第 4 节）；只提供「提示音开关」。
- 不改变各业务操作本身的行为。

**反目标（做成这样就算失败）**
- 刷屏：同一家店同一类状态问题每 5 分钟同步一次就再来一条。
- 强提醒被淹没：和「同步完成」这类弱通知混在一起、自动消失。
- 为了检测新订单 / 新售后而额外增加对抖店的请求频率（只在已有同步里比对）。
- 通知内容出现账号密码、cookie、完整手机号、卡号。

## 3. 现状（2026-11-26）

- 任务中心：`frontend/src/components/custom/task-center/`，纯前端状态机，吃 SSE 事件 `label_progress / label_done / ship_progress / ship_done / print_progress / print_done / ship_deadline_warning`。
- 后端事件总线 `service/events.py` + SSE `GET /api/events`（`api/event.py`）。现有事件还有 `shop_status_changed`（含 `egress_status`、`paused_reason`）、`shop_login_failed`、`sync_progress`、`reconcile_done`。
- 定时任务（`main.py` lifespan）：订单同步每 300 秒（`ORDER_SYNC_INTERVAL_S`）、会话探测每 1800 秒、临近超时扫描（`ship_deadline_scan_interval_s`，默认 1800）。
- 售后：只有手动「同步售后」，没有定时同步。
- 订单 / 售后入库：`order_store.upsert_orders`、`aftersale_store.upsert_aftersales`，返回条数，不区分新增与更新。
- 出口异常不会终止进程：`EgressUnavailable` → 该店 `egress_status=unreachable`、该店请求暂停；定时任务按店捕获异常继续；下一轮 `ensure_ready` 重查，代理恢复自动转 `ok`。

## 4. 提醒分档（所有者已确认）

| 档 | 表现 | 事件 |
|---|---|---|
| 强 | 状态类（登录失效、出口异常、风控暂停、临近发货超时、飞鸽会话超 3 分钟未回复）：全站顶部红色横条（问题未解决不消失）+ 提示音 + 页面在后台时发浏览器系统通知，不弹窗；事件类（新售后）：右下角弹窗不自动关闭 + 提示音 + 系统通知。都计入铃铛红色徽标 | 新售后 / 退货（含仅退款）；店铺登录失效；出口异常（不通 / IP 变化 / IP 重复）；风控暂停；临近发货超时；飞鸽会话超 3 分钟未回复 |
| 中 | 右下角弹窗几秒后自动消失；计入未读 | 新订单；批量打单 / 发货 / 打印有失败；同步失败；新消息（飞鸽）；飞鸽消息停止接收 |
| 弱 | 不弹窗，只进铃铛列表（也计入未读） | 批量操作全部成功；对账完成；同步完成 |

## 5. 做法（已选）

**后端存通知**（选定）：新增通知表；在已有同步与事件发生处写通知；通过现有 SSE 实时推送；前端铃铛读接口 + 订阅推送。

未选：**只在浏览器本地存**——改动小，但页面关闭期间的事全部丢失，且「新订单 / 新售后」必须由后端比对才能发现，满足不了需求。

## 6. 设计

### 6.1 两类通知

- **事件类**（一次性）：新订单、新售后、批量操作结果、同步失败 / 完成、对账完成。每次发生写一条；同一店同一类在短时间内合并（见 6.3）。
- **状态类**（持续存在直到恢复）：登录失效、出口异常、风控暂停、临近发货超时。每家店每类最多一条「未解决」记录（`state_key` 唯一）；问题持续时只更新 `updated_at` 与正文，不新增；恢复时置 `resolved_at` 并写一条弱档「已恢复」事件。顶部横条只显示未解决的强档状态类通知。

### 6.2 数据模型（新表 `notification`，迁移 0011 或当时的下一个编号）

| 列 | 说明 |
|---|---|
| id | 主键 |
| kind | 枚举，如 `new_order` `new_aftersale` `login_expired` `egress_unreachable` `egress_changed` `egress_duplicate` `risk_paused` `ship_deadline` `batch_done` `batch_failed` `sync_failed` `sync_done` `reconcile_done` `recovered` |
| level | `strong` / `medium` / `weak`（由 kind 决定，代码里一张映射表） |
| shop_id | 可空（跨店汇总时为空） |
| title / body | 展示文案；不得含敏感信息 |
| link | 前端路由 + 查询串（如 `/aftersale?view=todo&shop=3`） |
| count | 合并后的数量（新订单 5 单） |
| state_key | 状态类唯一键，如 `egress:3`、`login:3`；事件类为空 |
| resolved_at | 状态类恢复时间 |
| read_at | 已读时间 |
| created_at / updated_at | |

索引：`(read_at, created_at desc)`、部分唯一索引 `state_key WHERE state_key IS NOT NULL AND resolved_at IS NULL`。

保留策略：已读且超过 30 天的事件类通知随每日备份任务一起清理；未解决的状态类永不清理。

### 6.3 产生通知

- **新订单**：`order_sync` 入库前查出本批中库里不存在的订单号，按店合并成一条 `new_order`（「店A 新增 5 单待发货」）。订单同步本来只拉「待发货」（`sync_pending`），所以新订单天然就是待发货订单。基线规则见下条。
- **新售后 / 退货**：新增售后定时检查（与订单同频率，复用 `for_each_active_shop` + `run_every`）。每轮只调一次已有的售后计数接口（`AFTERSALE_COUNTS`，本来就有 60 秒缓存）；待办计数有变化时才跑一次完整售后同步（复用 `AftersaleService._sync_shop`）。比对出「库里没有、且状态属于待办」的售后单，按店合并为强档 `new_aftersale`；新出现但已关闭 / 已完成的历史单只入库不提醒。
- **基线（首次不提醒）**：新表 `sync_baseline(shop_id, kind, established_at)`，`kind` 为 `orders` / `aftersales`。某店某类第一次**完整**同步成功后写入（售后拉满页数上限仍未到底也算）；没有基线时只入库不提醒。这样「有订单但从没有售后」的店，第一笔售后不会被吞（基线在第一次完整售后同步时建立，哪怕结果为 0 条）；同步中途失败不建基线。
- **登录失效**：`SessionManager.mark_expired`（及登录失败事件）→ 状态类 `login:{shop}`；扫码登录成功 → 恢复。
- **出口异常**：`EgressService` 写入 `unreachable / changed / duplicate` 时 → 状态类 `egress:{shop}`（正文写具体原因）；转 `ok` → 恢复。
- **风控暂停**：`ShopRunner._pause` → `risk:{shop}`；`resume` → 恢复。
- **临近超时**：现有 `ShipDeadlineWatcher` 扫描结果 → 状态类 `deadline:{shop}`，数量为 0 时恢复；停用店的订单不计，店铺停用时一并恢复。
- **启动对账**：应用启动后对每个店铺按当前状态对账一次，补上升级前已有或停机期间丢失的状态类问题。
- **批量操作**：`label_done / ship_done / print_done` 汇总 → 有失败为中档 `batch_failed`，否则弱档 `batch_done`。
- **同步 / 对账**：同步失败中档、成功弱档（仅手动触发的同步写「完成」，定时同步成功不写，避免每 5 分钟一条）；对账完成弱档。

- **状态反复（防刷屏）**：同一 `state_key` 恢复后 30 分钟内再次出问题，重新打开原记录（清 `resolved_at`、横条重新出现），但不再响铃、不再发系统通知、不写新的「已恢复」事件；超过 30 分钟才当作新问题走完整强提醒。
- **写入位置**：批量操作结果由后端服务在批次结束时写一次（label / ship / print 的 done 处），前端不写通知，多标签页不会重复。「进行中」进度仍只在前端内存，不持久化。

统一入口：`service/notifications.py` 的 `NotificationService.emit(...)` / `raise_state(...)` / `resolve_state(...)`，写库后通过事件总线发 `notification` SSE 事件。各业务服务只调用它，不直接写表。

### 6.4 接口

- `GET /api/notifications?unread=1&page=` 列表（新的在前）
- `GET /api/notifications/summary` → `{unread, strong_open: [...]}`（铃铛数字 + 顶部横条）。`unread` 不含未解决的强状态（横条 / 待处理已代表它们），解决后照常计入；`strong_open` 每店带 `problems: [{kind, link}]`。
- `POST /api/notifications/{id}/read`、`POST /api/notifications/read-all`
- SSE 事件 `notification`（新增 / 更新 / 恢复）

### 6.5 前端

- 页面标题行右侧放铃铛图标按钮（纯图标按钮规则：无背景），未读数徽标；强档未解决时徽标为红色。原「店铺正常 / N 家店需处理」状态胶囊已去掉（与横条、铃铛重复）。
- 点开为右侧弹出面板：顶部「进行中」区（迁自任务中心：批量操作进度条与计数），下面「待处理」区（未解决的状态类，固定置顶），再下面按时间的通知列表（未读加粗、点击已读并跳转 `link`）、「全部已读」。
- 顶部横条：全站页面最上方，列出未解决的强档状态类，**一店一行**，同一行列出该店所有问题（如「店A：登录失效、出口不通」）；超过 3 家时合并为「N 家店需要处理」并展开在铃铛面板。每个问题单独可点，按问题类型跳转：登录 / 出口 / 风控 → 店铺管理并高亮该店（新增 `?shop=<id>` 支持），临近超时 → 全部订单的「超时未发」筛选（该店有已超时订单时）或「24 小时内须发」筛选。问题恢复自动消失，不可手动关闭。
- 右下角弹窗：复用现有浮动提示组件；只弹事件类——强档（新售后）不自动关闭，中档 5 秒自动关闭，弱档不弹。状态类强提醒（有 `state_key`）只上横条、响提示音、发系统通知，不弹窗。
- 页面「N 家店未取到」提示（订单、售后、商品计数、仪表盘）不列已在横条里有登录 / 出口 / 风控问题的店，都在横条里时整条不显示；读同一份摘要缓存，不多发请求。
- 提示音 + 浏览器系统通知：仅强档；系统通知只在页面不在前台时发；首次需要时请求通知权限；面板里一个「提示音」开关（存本地）。
- 删除侧栏「任务」入口与 `task-center` 目录，进度状态机迁到通知模块的 hooks/logic。

### 6.6 单操作员

本应用只有一个管理员账号（`admin_user`），`read_at` 全局一份即可；多个浏览器标签页通过 SSE 同步已读状态。

## 7. 约束

- 不为检测新事件增加额外的抖店请求：售后检查每轮只多一次计数请求，计数变化才全量同步；遵守每店串行、出口检查与风控暂停。
- 文案遵守「不写说明小字」；通知正文只写事实（店名、数量、原因），不写操作建议长句。
- 文件长度、分层、测试规则同 engineering-rules。

## 8. 留给实现者

- 合并窗口（同店同类新订单在多长时间内合并到同一条未读通知）：建议「该店最近一条同类通知仍未读则累加到它上面」。已实现为此规则；合并后数量变多的新订单 / 新售后仍弹窗 / 响铃。
- 提示音素材与音量；系统通知的图标。
- 弹出面板的具体视觉，按 ui-guidelines 与现有抽屉 / 弹层组件。
