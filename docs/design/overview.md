# 总体设计

> 抖店多店铺管理后台的定位、范围、架构、技术栈、测试、里程碑、验收与风险。
> 文档索引与章节对照见 [docs/README.md](../README.md)。
> 2026-11-03 初版；2026-11-25 整理：合并原 `architecture.md` 与 `overall-design.md`，章节号沿用原 `architecture.md`。

## 0. 一句话说明

给管理**多家不同主体的抖音小店**的商家，做一个**本机运行的多店管理后台**：把订单、售后、商品、库存、资金、对账聚合到同一个界面，替代「逐个登录每个店后台、重复操作」的日常劳动。

前端用 Arc 组件库（`uiarc-system`）搭完整后台，后端在本机代理所有抖店请求，数据与登录态全部留在本机。

## 1. 背景与目标

### 1.1 背景

抖小宝等「抖店商家助手」把多店管理做成 PC 客户端。其核心价值不是某个单点功能，而是：

- **一个后台管理多家店**，免去反复登录切换；
- 把**重复的批量操作**自动化，降低人力成本；
- 数据留存在商家本机，登录态走商家自己的网络环境。

本项目为**自用工具**，不对外售卖，因此不需要授权、计费、自动更新、反破解等商业化设施，全部精力投入"把活干成"。

### 1.2 目标

| 目标 | 衡量方式 |
|---|---|
| 多店订单聚合 | 一个界面看到所有店的待发货订单 |
| 批量取号 | 勾选 N 单，一次操作完成全部取号 |
| 批量打印 | 按店铺/快递分组打印，面单与店铺对应关系零错误 |
| 发货回传 | 人工确认后一次点击，全部订单回写平台为"已发货" |
| 安全可控 | 取号与发货分离；重复取号/重复发货为 0 |
| 可维护 | 抖店接口变化时，只改 `adapter/doudian/`（含签名子目录） |

### 1.3 已确认的业务前提

1. 多店**分属不同营业执照主体**，需分别登录，每店独立会话。
2. 电子面单**已开通**，快递公司**已绑定**，无需对接快递公司开放平台。
3. 打印机与打印方式已在各店后台配置好（具体打印实现见第 10 节）。
4. 采用**半自动**模式：软件负责取号等可逆动作，发货回传由人工最终确认。

## 2. 范围

### 2.1 MVP 范围（本设计覆盖）

**会话与基础**
- 本机管理员账号登录（单账号；首次运行创建，[backend.md](backend.md) 5.16）
- 每店独立环境：独立浏览器 profile + 固定独立出口 IP（[backend.md](backend.md) 5.17）
- 多店扫码登录与会话持久化，Cookie 导出供协议层使用
- 会话健康检测与一键重登
- 基础数据同步：发货地址、面单模板、快递公司、店铺配置

**订单履约**
- 待发货订单同步（手动 + 定时）
- 多店订单聚合池（筛选、勾选）
- 收货地址解密（`/api/order/receiveinfo`）：**按需**，仅用户查看收件人或自渲染 PDF 时调用（DEC-06）
- 批量取电子面单号
- 面单打印（官方打印组件 `wss://localhost:13999`；自渲染兜底）
- 发货前检查 + 发货回传（人工确认）
- 面单作废与重新取号（作废接口已验证，见 [api/write.md](../api/write.md) A.2.6）
- 每日对账
- 操作审计日志、限速、演练模式

**多店聚合（只读）**
- 售后聚合：列表、详情、状态计数、待办队列（[附录 E](../api/aftersale.md)）
- 商品管理：列表、状态计数、分组、类目（[附录 D](../api/catalog.md)）
- 库存管理：列表、现货/未来库存、预警（[附录 D](../api/catalog.md)）
- 资金看板：账单查询、多店概览（[附录 F](../api/fund.md)）
- 跨店对账：快照比对、三类异常（[附录 G](../api/reconcile.md)）

**前端**
- 完整后台界面（React + Arc 组件库），见 [frontend.md](frontend.md)

### 2.2 非目标（明确不做或延后）

| 内容 | 去处 |
|---|---|
| 售后处理动作（同意退款、填运单号等写接口） | 阶段二 |
| 商品创建 / 编辑 / 上下架（写接口） | 阶段二 |
| 物流轨迹、改物流、批量备注、合单发货 | 阶段二 |
| 营销活动、优惠券、千川/联盟推广 | 阶段三 |
| 客服 IM（飞鸽）、评价管理 | 阶段三 |
| 直播管理、店铺装修、供应链 | 不做 |
| 对外授权、多租户、多账号与角色权限、计费 | 不做（本机管理员登录已纳入 MVP，见 2.1） |
| 移动端 | 不做 |
| 跨平台（快手/淘宝/拼多多） | 不做 |

> 说明：非目标中的功能大多可在「渠道适配层 + 任务队列」之上扩展；写接口因涉及资金与平台风控，统一放在只读链路验证完成之后。

| **阶段二** | 售后处理动作、商品写操作、物流轨迹、改物流、批量备注、合单发货、通知通道 |

## 3. 假设与约束

| 编号 | 假设 | 影响 |
|---|---|---|
| A1 | 店铺数量 5~50 家 | 每店一条串行队列；SQLite 单库足够 |
| A2 | 单店日单量 10~500，总日单量 < 5000 | SQLite + WAL 可支撑；超过需迁移 PostgreSQL |
| A3 | **开发机 ≠ 出单机** | 打印与真实取号在出单机验证；交付时整体拷贝 |
| A4 | 每个店首次由人工扫码登录，之后持久化 | 掉线重登是日常运维动作，必须第一版就有 |
| A5 | 出单机为 Windows 10/11 | 打印优先走官方打印组件；兜底走 Windows 打印子系统 |
| A6 | 每店一个固定独立出口：最多一家用商家自有宽带直连，其余用独享静态代理（DEC-11） | 出口不轮换；会话只在建立它的出口上使用 |

## 4. 总体架构

### 4.1 运行形态

单机、单进程、本地访问。软件运行在**出单机**（Windows 10/11）。

```
┌─────────────────────────── 出单机 ───────────────────────────┐
│                                                               │
│  浏览器 ──HTTP/SSE──► 后端进程（FastAPI + uvicorn，127.0.0.1:8787）│
│                         │  ├─ 托管前端静态文件（Vite 构建产物）     │
│                         │  ├─ 本地 API /api/*                   │
│                         │  └─ 后台任务（每店串行队列 + 定时器）     │
│                         │                                       │
│        ┌────────────────┼──────────────────┬─────────────────┐  │
│        ▼                ▼                  ▼                 ▼  │
│   SQLite (WAL)    curl_cffi 协议直连   Playwright + Edge   打印组件  │
│   data/app.db     ──► fxg.jinritemai   每店独立用户目录      wss://localhost:13999
│                                       （扫码 / 兜底 / 借页打印）  │
└───────────────────────────────────────────────────────────────┘
```

**本机数据目录**（全部不入库）。下表的 `data/` 指数据目录：Windows 默认 `%LOCALAPPDATA%\doudian-multishop\`，其他平台默认仓库根的 `data/`，可用环境变量 `DD_DATA_DIR` 覆盖。不放在仓库或桌面下，避免被 OneDrive 等同步到云上。

| 路径 | 内容 |
|---|---|
| `data/app.db` | SQLite 主库 |
| `data/profiles/<shop_id>/` | 每店独立的浏览器用户目录（登录态 + 指纹隔离） |
| `data/backups/` | 每日数据库快照 |
| `logs/` | 运行日志（已脱敏） |

**约束**：后端只监听 `127.0.0.1`，不对局域网开放；除登录相关接口外，所有本地 API 都要求管理员登录（[backend.md](backend.md) 5.16）。

### 4.2 分层原则

- 界面层不直接访问抖店，只调用本地 API（[local-api.md](local-api.md)）。
- 应用服务层只编排业务，不关心请求怎么发出去。
- 渠道适配层是唯一与抖店交互的地方。
- 存储层只负责持久化，不含业务判断。
- **写操作与读操作分离**：聚合模块（售后/商品/库存/资金/对账）全部只读，
  写操作（取号/发货/作废/售后处理）单独走任务队列，先预览、人工确认后执行（[backend.md](backend.md) 5.11）。

后端分层与模块见 [backend.md](backend.md) 5.0，目录与命名以 [engineering-rules.md](../engineering-rules.md) 为准。

## 11. 技术栈与目录结构

### 11.1 后端

| 用途 | 选型 |
|---|---|
| 语言 | Python 3.12 |
| Web 框架 | FastAPI + uvicorn + Pydantic v2（接口 + 托管前端静态文件） |
| 抖店协议 | curl_cffi（`impersonate="chrome"`），经可替换的 Transport 调用（测试用录制回放） |
| 浏览器 | Playwright（Python）+ 系统 Edge（`channel="msedge"`），每店持久化用户目录 |
| 签名 | py_mini_racer（V8）——**备用**，已验证的写接口免签名，不进 MVP 主路径 |
| 打印组件 | `websockets`，`wss://localhost:13999` |
| 数据库 | SQLite WAL + SQLAlchemy 2 Core + Alembic |
| 调度 | asyncio（每店队列 + 全局信号量 + 进程内定时循环），不引入 Celery / APScheduler |
| 日志 | structlog + 统一脱敏处理器 |
| 凭证加密 | Windows DPAPI |
| 测试 | pytest + pytest-asyncio + 录制回放 Transport |
| 打包 | PyInstaller 单目录模式 + 启动脚本（⏳ 细节见 gaps ENG-04） |

### 11.2 前端

React 19 + TypeScript + Vite + Tailwind CSS 4 + Arc 组件库 + TanStack Query + React Router，
接口类型由 openapi-typescript 从后端生成，实时推送用 SSE。完整说明见 [frontend.md](frontend.md)。

## 12. 测试策略

| 层级 | 内容 | 方式 |
|---|---|---|
| 单元测试 | 状态机流转、幂等键、DTO 解析、地址校验 | pytest，使用 `raw_json` 真实样本 |
| 集成测试 | 渠道接口 → 服务层 → 数据库 | 录制回放：mock 抖店响应 |
| 契约测试 | `protocol` 与 `browser` 两个渠道行为一致 | 同一组用例跑两个实现 |
| 真实环境验证 | 拉单、取号、发货、作废、取号发货一体、改物流已用测试单验证（[api/write.md](../api/write.md)）；多单 / 多 SKU / 合单待测（gaps API-06 / 09） | 用测试店铺真实执行 |
| 手工验收 | 2 个店各 1 单全流程；错单/掉线/作废场景 | 人工按验收清单执行 |

**重点测试项**：

- 重复点击"取号"不会产生两张有效面单。
- 重复点击"确认发货"不会重复发货。
- 会话失效时只影响该店。
- 面单作废后订单能回到 `pending_label`，且能再次取号（防重键不冲突，[backend.md](backend.md) 5.11）。
- 取号超时后走「查回运单号」恢复，不会重复取号、不会误转 `exception`（[backend.md](backend.md) 5.5）。
- 平台已取消 / 已关闭的订单不会进入取号批次（`orders.platform_status`，[backend.md](backend.md) 5.4）。
- 对账能发现人为制造的三类异常。
- 取号、发货、官方组件打印全流程不发出任何 `receiveinfo` 请求（DEC-06）。
- 模板/地址缺失时，取号前即被拦截。
- 打印组件未启动时，订单不会被标记为已打印。

## 14. 验收标准

1. 至少 **2 个不同主体店铺**各完成 1 单全流程（拉单 → 取号 → 打印 → 发货）。
2. 取号成功率 > 98%（分母 = 已进入取号批次且预检通过的订单；超区/地址异常/余额不足等业务拒绝类不计入分母）。
3. 连续点击"取号"/"确认发货"各 5 次，无重复面单、无重复发货。
4. 手动使某店会话失效，系统在 5 分钟内标记 `needs_login`，其他店不受影响。
5. 对账能发现人为制造的三类异常。
6. 所有外部调用均可在审计日志中追溯。
7. 软件在出单机上双击启动即可使用，无需命令行操作。
8. 基础数据（地址 / 模板 / 快递）能自动同步，并在取号时正确匹配到本店配置。
9. 面单上打印出完整收件信息：官方组件打印由 `print_data` 渲染，**不经本地解密**；自渲染 PDF 兜底时按需解密（DEC-06）。
10. 打印组件未启动时，界面明确提示，且**不会**把订单标记为已打印。
11. 演练模式（dry-run）下不产生任何真实取号或发货请求。

## 15. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 接口强制签名 | 已验证的 7 个写接口免签名；`searchPackageList` 等个别接口需签名 | 逐接口验证并在 `endpoints.py` 声明；需签名的走浏览器通道，必要时再启用签名引擎 |
| 平台风控关联判定 | 账号受限 | 每店独立 profile + 固定独立出口、设备参数一致、限速、工作时段、操作留痕；异常即停。是否符合平台规则由所有者判断（DEC-11） |
| 代理出口故障或被换 IP | 该店无法同步 / 会话风险 | 每轮任务前检查出口；不通或 IP 变化即暂停该店，不退回直连 |
| 官方打印组件接口变化 | 打印失败 | 保留 PDF 兜底（方案 B）与手动打印（方案 C） |
| 地址解密接口变更 / 额度用尽 | 无法查看收件人、自渲染 PDF 缺明文地址（取号与官方打印不受影响，DEC-06） | 解密失败只提示，不改订单状态；引导到官方页面查看或申请提额 |
| 抖店后台改版 | 接口失效 | `adapter/doudian/` 与 `adapter/doudian/signing/` 隔离，替换适配器 |
| 登录频繁过期 | 运维负担 | 重登流程简化（一键弹窗）+ 到期提醒 |
| 开发机无打印机/打印组件 | 无法本地验证打印 | 打印在出单机验证；开发期用 dry-run + PDF 预览 |
